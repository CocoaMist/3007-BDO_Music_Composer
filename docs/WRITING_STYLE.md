# 文档说话方式 ♪

这不是一套“写得像说明书”的模板，而是这个仓库统一的说话方式。先把事情讲明白，
再补证据和规则；能一句说完，就不要绕三句 `( •̀ ω •́ )✧`

## 写给谁看

- 首页和语言指南写给作曲玩家：先告诉他能做什么、怎么开始、哪里要小心。
- 开发指南写给维护者：先给结论和入口，再放命令、边界与验证。
- 算法、格式和基准文档写给复核者：事实、推断和未验证内容必须分开。
- 历史记录、旧版发布说明和第三方许可属于证据，不为了统一语气篡改原文。

## 具体怎么写

1. **先说结论。** 不用“本文旨在”“本项目致力于”暖场。
2. **说人话。** 能用“会”“不会”“要”“别”时，不换成“提供能力”“确保”“赋能”。
3. **一段只做一件事。** 背景、操作、风险和证据不要揉成一团。
4. **少报喜，多交代边界。** 测试通过就写通过了什么；没进游戏验证，就直接写没验证。
5. **名称保持稳定。** `TrackState`、Clip、BDO v9、Owner ID 等领域词不硬翻译，也不造同义词。
6. **颜文字只放在入口和轻松提示里。** 技术错误、隐私、许可、数据损失和安全警告不卖萌。
7. **链接只留有用的。** 同一入口不要在一页反复出现，细节交给对应文档。

## 尽量删掉的高频套话

下面这些词不是禁词，但连续出现通常说明句子还可以再短一点：

- “当前”“完整”“全面”“统一”“确保”“保持”；
- “能力”“方案”“策略”“工作流”“边界”“可审查”；
- “robust”“seamless”“comprehensive”“deliberately”“remains”。

例如：

- “确保当前编辑状态能够完整地贯穿工作流” → “试听、保存和导出都读取正在编辑的音符”。
- “提供可审查的优化能力” → “先预览改动，确认后再写入音符”。
- “保持确定性并确保安全” → “相同输入得到相同结果；失败时不写文件”。

## 可爱，但别碍事

这个项目可以有一点猫味，也可以有一点作者脾气。首页、入门提示和感谢里偶尔出现
`ฅ^•ﻌ•^ฅ` 没问题；真正影响作品、隐私或游戏兼容性的地方，直接讲清楚更可爱。
