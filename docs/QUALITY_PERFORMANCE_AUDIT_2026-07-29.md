## 已修复问题

### 1. 实时效果路径的重复插值与逐帧开销

问题：非零 Aux Send 会让声部退出固定八声部插值瓦片和等价声部合并；Reverb、Delay、Chorus 又在 Python 中逐帧访问 NumPy 标量。三效果同时开启时，这两部分叠加占用了过多音频预算。

处理：

- 效果声部继续使用固定批量插值，随后按逻辑声部路由 Aux Send。
- 完全相同的路由按瓦片聚合；完全等价的声部使用 `Σ(gain × send)` 聚合湿声，但仍逐声部维护生命周期、实例限制、Seek 状态和轨道电平。
- 四条 Reverb 延迟线改用配置期预分配的有界标量环形缓冲，保留原反馈/阻尼方程。
- Delay 和 Chorus 改为固定 4096 帧 scratch 上的有界向量分块；分块不超过环形回绕和最小调制延迟，因此反馈顺序保持不变。
- 新增批量/等价路径与强制标量路径的逐样本对比，以及热路径禁止 NumPy 缓冲分配和逐帧 `math.sin` 的回归测试。
- 修复等价探针命中后其余单例声部绕开瓦片的问题：重复组继续精确聚合，单例重新进入固定八声部插值瓦片；新增同时包含重复组和大量非重复单例的逐样本、轨道峰值与生命周期对照测试。

同机、device-free、36 kHz、2048 帧块、三效果全开结果：

| 工作负载 | 优化前 P95 | 优化后 P95 | 优化后音频预算占比 | 优化后实时倍数 |
|---|---:|---:|---:|---:|
| 64 声部 | 约 22.5 ms | 约 7.94 ms | 约 14.0% | 约 7.45× |
| 176 声部 | 约 33.6 ms | 约 9.85 ms | 约 17.3% | 约 7.13× |

效果处理器自身的三效果耗时从约 18.4 ms/块降到约 4.4 ms/块，下降约 76%。以上是合成 PCM 和本机 CPU 证据，不代表游戏 DSP 声音已经 A/B 验证，也不替代目标声卡实测。

合法本地游戏样本、全效果、device-free、多乐器同起压力结果：

| 请求声部 | 已映射事件 / 峰值声部 | 准备耗时 | P95 | 实时倍数 | 声部窃取 |
|---|---:|---:|---:|---:|---:|
| 64 | 58 / 57 | 约 149 ms | 约 5.01 ms | 约 6.25× | 0 |
| 176 | 160 / 153 | 约 212 ms | 约 13.36 ms | 约 4.77× | 0 |
| 256 | 232 / 219 | 约 226 ms | 约 16.04 ms | 约 3.97× | 8 |

三档均为 0 underrun。单例重新进入瓦片后，176 档 P95 从约 15.41 ms 降至 13.36 ms，256 档从约 20.79 ms 降至 16.04 ms。256 档的 8 次窃取来自生产声部上限策略，不是无界增长或调度失败。基准可通过 `tools/benchmark_realtime_audio.py --mode offline --workload multitrack --effects` 复现；JSON 同时记录平台、Python、PySide、NumPy 和固定效果参数，脚本明确拒绝把尚未准备完成的效果负载用于 sink 模式。

### 2. 优化器污染调用方配置

问题：`optimize_tracks()` 会就地改写传入配置的 `level`、`game_safe_only` 和 `allow_track_creation`，使复用同一个配置对象的后续预览依赖调用历史。

处理：优化入口先复制配置，再在执行副本上规范兼容字段；新增配置复用回归测试。优化结果语义不变，调用方状态保持稳定。

### 3. 主页曲谱摘要的总轨道预算

问题：目录摘要只限制单组轨道数，没有限制所有组的物理轨道总数。畸形文件可以在每组都不超限的情况下触发大量独立 ICE 块解密。

处理：只在轻量摘要接口增加 4096 条物理轨道的总预算；完整编解码接口不受影响。超限文件只失去主页徽标，不会被静默当作有效曲谱。

### 4. 主页曲谱摘要的读取竞态

问题：先 `stat()` 再 `read_bytes()` 无法保证实际读取仍小于 2 MiB；文件可能在两次调用之间被替换或增长。

处理：直接有界读取 `2 MiB + 1`，超限立即返回空摘要，保证内存与解析成本上限。

### 5. 可持续的密集 UI 性能基准

新增 `tools/benchmark_dense_ui.py`，默认使用 Qt offscreen 固定测量 48k 音符时间轴、12k 主音符 + 8k 幽灵音符钢琴卷帘，以及 12k/50k/100k 音符索引与晚段查询。脚本输出平台、Python、PySide、负载规模和耗时分布 JSON；单元测试只验证工作负载与结果结构，不把易受调度影响的 wall-clock 数字硬编码成脆弱门槛。

本机复跑的稳定结果：

- 48k 时间轴索引构建约 15.8 ms，绘制中位数约 14.2 ms、P95 约 15.9 ms，单轨查询检查 400 条候选。
- 12k + 8k 钢琴卷帘绘制 P95 约 7.94 ms，可见主音符 118、幽灵音符 85。
- 12k/50k/100k 晚段查询 P95 分别约 0.015/0.028/0.040 ms；100k 索引构建约 42.7 ms，查询只返回 42 条音符。
- 一次独立时间轴运行出现约 41 ms 的系统调度尖峰，复跑恢复至约 16 ms P95；因此正式门继续以可见区检查数和缓存不变量为主，耗时分布为辅。

### 6. 10 万音符 autosave 预算

10 万音符快照在 GUI 线程约 0.56 ms、峰值临时内存约 0.77 MiB；开启 `tracemalloc` 时，后台原子 JSON 写入约 1.89 秒、峰值临时内存约 10.1 MiB，生成项目约 2.34 MiB。当前设计只允许一个后台 writer，并把并发期间的中间请求共并为最新不可变快照，因此慢盘不会形成无界 writer 队列；关闭流程仍显式排空当前与最新待写请求。
